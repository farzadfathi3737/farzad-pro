معماری V2Gate

سرور تک‌پورتی VLESS/Trojan با موتور بومی Node.js، پنل کانفیگ و پشتیبانی از IP تمیز — از مسیر یک بسته در شبکه تا بایت‌های داخل هر فریم. نقشه‌ها با استقرار فعلی شما کشیده شده‌اند: دامنه‌ی rasta1.gostarantablo.com روی Cloudflare Worker، هاست Node در 6f75r4.bot-keep.xyz.

۱ مسیر کامل یک اتصال

کلاینت هیچ‌وقت مستقیم به هاست وصل نمی‌شود. TLS را Cloudflare خاتمه می‌دهد، Worker درخواست را به هاست می‌فرستد، هاست TLS دوم را خاتمه می‌دهد و درخواستِ خام HTTP را به پورت داخلی Node تحویل می‌دهد. نقطه‌ی حساس برای فیلترینگ فقط هاپ اول است؛ بقیه‌ی مسیر بیرون از ایران است.

هاپ TLS سمت کلاینت (جایی که IP تمیز اثر دارد)Worker (بازنویسی Host)مرز اعتماد
نکته‌ی IP تمیز: کلاینت به IP تمیز وصل می‌شود ولی در TLS Client Hello مقدار SNI و در هدر HTTP مقدار Host همان rasta1.gostarantablo.com است. Cloudflare فقط به این دو نگاه می‌کند، نه به IP مقصد؛ پس هر IP لبه‌ی Cloudflare که از ISP شما باز باشد، کار می‌کند.

۲ داخل پروسه‌ی V2Gate

یک پروسه‌ی Node، یک سرور HTTP روی $PORT. دو رویداد جدا دارد: request برای صفحات (پنل، سابسکریپشن، صفحه‌ی پوششی) و upgrade برای ترافیک پروکسی. مسیر پروکسی هرگز وارد روتر HTTP نمی‌شود و برعکس.

چرا دو ترنسپورت؟

WebSocket از همه‌ی CDNها و کلاینت‌ها رد می‌شود ولی هر بسته ۲ تا ۱۴ بایت سربار فریم دارد. HTTPUpgrade همان دست‌دادن HTTP را می‌کند و بعد از 101 بایت‌ها خام می‌روند — کمتر سربار، ولی بعضی CDNها آن را نمی‌شناسند. هر دو با یک Upgrade header می‌آیند؛ تفاوت فقط در این است که بعد از 101 فریم‌بندی داریم یا نه.

چرا مسیرها از UUID ساخته می‌شوند؟

اسکنرها به /ws و /vless درخواست می‌زنند. مسیر /vless-6578858c حدس‌زدنی نیست، و درخواست بدون Upgrade به آن هم مثل هر مسیر دیگری ۴۰۴ می‌گیرد — سرور از بیرون شبیه یک اپ ساده‌ی Node است.

احراز هویت پروکسی

VLESS با مقایسه‌ی ۱۶ بایت UUID، Trojan با مقایسه‌ی ۵۶ کاراکتر SHA-224 رمز؛ هر دو با timingSafeEqual. اتصالِ رد‌شده بی‌صدا بسته می‌شود (بدون پاسخ متمایز) و در stats.errors شمرده می‌شود.

پس‌فشار (backpressure)

اگر مقصد کند باشد، stream.pause() تا drain؛ اگر کلاینت کند باشد، target.pause(). WebSocketStream هم با push() برگشتی false سوکت زیرین را pause می‌کند. حافظه با تعداد اتصال رشد نمی‌کند.

۳ توالی برقراری یک اتصال

یک درخواست کلاینت برای باز کردن example.com:443 از طریق VLESS-WS، قدم‌به‌قدم. زمان از بالا به پایین است. دو TLS جدا وجود دارد و فقط اولی را کلاینت می‌بیند.

۴ ساختار بایت‌ها

سه لایه‌ی فریم‌بندی روی هم سوارند: فریم WebSocket (ترنسپورت)، هدر پروتکل (یک‌بار در ابتدای اتصال)، و payload. proxy.js فقط دومی و سومی را می‌بیند.

۵ تنظیمات، state و اولویت‌ها

سه منبع تنظیم وجود دارد و ترتیب غلبه‌شان بیشتر اشکال‌های استقرار را توضیح می‌دهد. مقدارهایی که در هیچ‌کدام نباشند یک‌بار تولید و در data/state.json ذخیره می‌شوند؛ اگر دیسک هاست پایدار نباشد، با هر دیپلوی عوض می‌شوند.

۶ تولید کانفیگ و سابسکریپشن

کانفیگ‌ها ذخیره نمی‌شوند؛ هر بار از روی state ساخته می‌شوند. تعداد خروجی = (پروتکل‌های فعال) × (۱ + تعداد IP تمیز). همه در یک سابسکریپشن می‌روند تا کلاینت خودش بهترین را با URL-test انتخاب کند.

۸ مرزها و محدودیت‌ها

  • UDP فقط DNS. بازی و تماس صوتی که UDP خالص می‌خواهند کار نمی‌کنند؛ مرور، ویدیو، پیام‌رسان‌ها از TCP می‌روند و مشکلی ندارند. (علت: Cloudflare و هاست‌های HTTP فقط جریان TCP/WebSocket را عبور می‌دهند.)
  • VMess و Shadowsocks نیستند. هر دو رمزنگاری در لایه‌ی پروتکل دارند که در این معماری ارزشی اضافه نمی‌کند، چون TLS بیرونی همه‌چیز را پوشانده است.
  • Reality/XTLS ممکن نیست. نیاز به کنترل مستقیم سوکت TLS دارند؛ پشت Cloudflare یا پروکسی هاست، TLS در اختیار ما نیست.
  • دو TLS پشت سر هم (کلاینت→Cloudflare، Worker→هاست) یعنی تأخیر دست‌دادن کمی بیشتر از اتصال مستقیم؛ بعد از برقراری، جریان داده پیوسته است.
  • Worker حالت ندارد و هر اتصال WebSocket یک «درخواست» در سهمیه‌ی روزانه حساب می‌شود، نه هر بسته.
  • state روی دیسک ناپایدار با هر دیپلوی عوض می‌شود؛ راه‌حل، دادن UUID / TROJAN_PASSWORD / SUB_TOKEN / PANEL_PASSWORD در env است.
  • مرز اعتماد: سرور محتوای داخل اتصال‌های TLS کلاینت را نمی‌بیند، ولی مقصد (دامنه/IP و پورت) هر اتصال را می‌داند و در حالت VERBOSE=1 لاگ می‌کند. پنل و سابسکریپشن فقط با رمز/توکن در دسترس‌اند و روی هر مسیر دیگری سرور خودش را یک اپ ساده نشان می‌دهد.
